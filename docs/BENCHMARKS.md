## Method, and what the axis licenses

The primary axis is **warm wall-clock seconds**, reported alongside `ESS_worst` (worst-parameter
bulk ESS, `whisper_cbpf.metrics.ess_summary`) and `ESS_worst/s` computed from the **warm** time
only. Compile is never amortised into a per-sample figure, and no per-sample figure is computed
from a cold time. With `--two-stage` each cell's budget knob is rescaled from a pilot run so the
cells are compared at a matched posterior-quality target (`ESS_worst >= 400`).

**ESS/s is not a ranking key on its own.** ABC, ABC-SMC and SNPE target *approximations* of the
posterior; their draws are near-independent, so `ESS ~ n_draws` and their ESS/s is enormous — for
draws from the wrong distribution. A row whose accuracy verdict is not `PASS`, or whose ESS is
`iid_assumed` (no chain axis), has its ESS/s struck through and is excluded from any speed ranking.
This is the single most important honesty rule in the design.

**Axes deliberately rejected.** *Fixed forward-model evaluations* cannot be controlled: NUTS's
evaluation count is adaptive, and in this repository it is not even knowable after the fact
(`nuts_gpu.py` never collects `num_steps`). A NUTS evaluation is also a *gradient* evaluation
(~2-4x a forward one) while `abc_gpu`'s are batched 16 wide — so equal counts would be
conspicuously unequal work, which is the effect under study. Evaluations are reported as a
covariate instead. *Fixed wall time, compare quality* needs a pilot run anyway, and then compares
at a budget no sampler was tuned for; the two-stage design spends that same pilot on
quality-matching, which answers the more useful question.

**What a passing row licenses:** "On AT2017GFO as selected here, for *this* model, on *this* box
and *this* card, at *this* budget, sampler X produced N effective samples of its worst-constrained
parameter in T warm seconds."

### Instruments

| quantity | instrument | exact or sampled |
|---|---|---|
| wall time | `time.perf_counter()` around `wp.fit` only | exact |
| cold start | `t_cold - t_warm` across repeats in one process | derived. **Upper bound on XLA compile, not a compile measurement**: it also absorbs allocator first-touch, autotune and first-call library imports inside the metrics, and is nonzero on pure-numpy cells where nothing compiles |
| model warm-up | one blocked `model.predict` at the prior median before any timer | exact |
| peak GPU memory | `jax.Device.memory_stats()['peak_bytes_in_use']`, `torch.cuda.max_memory_allocated()` | exact |
| GPU contention | `nvidia-smi` polled every 1.0 s | **SAMPLED estimate, not an integral** |
| CPU core-seconds | `getrusage(SELF)+getrusage(CHILDREN)` delta across the fit | exact |
| ESS | `whisper_cbpf.metrics.ess_summary` (arviz bulk, worst parameter) | exact |
| accuracy | `sbi.utils.metrics.c2st` + normalised 1-Wasserstein vs a cached reference | exact when a reference exists, otherwise *not measured* |

Struck-through `ESS_worst/s` means the row is **excluded from any speed ranking**: either its ESS is `iid_assumed` (no chain axis — ABC/ABC-SMC/SNPE), or its accuracy gate did not return PASS. `WAIC !` marks a WAIC whose own `p_waic` says it is unreliable — the same convention as `scripts/compare_at2017gfo.py`. A row with `trust = contended` shows `-` for every timing rather than a number nobody can reproduce.

## GPU trace — the sampled half

`nvidia-smi` polled every 1.0 s for the lifetime of each GPU worker (import, warm-up, every repeat and the metrics — not only the timed fit, so mean utilisation is diluted by setup). **These are sampled estimates, not integrals**, and a cell shorter than a few periods gets a handful of points; the sample count is in the table so nobody reads a mean off two of them.

`smi peak MiB` is *not* the per-process peak — under this repo's `whisper-gpu-env.sh` XLA preallocates `XLA_PYTHON_CLIENT_MEM_FRACTION` of the card, so `nvidia-smi` reports the pool. The exact per-process peak is the `GPU peak MiB` column of the group tables, from `jax.Device.memory_stats()['peak_bytes_in_use']`. `excess MiB` is what was on the card beyond our own pool and the pre-run baseline; over 2048 MiB is called contention. That threshold is measured, not assumed — see *Known measurement gaps*.

`--validate-evals` registers `bazin__counted`, whose `predict` increments a counter, and compares the observed call count with the ledger's `fit_evals + overhead_evals`. ## Crossover (Group D)

**Not measured in this run.** `docs/CHOOSING.md:19` asserts "the GPU crosses over at roughly 50,000 simulations" and no measurement supporting it exists anywhere in this repository. Run `--crossover` to test it; the harness fits `wall(N) = a + b*N` per arm on the warm runs, solves for `N*`, bootstraps a 95% CI over the repeats, and reports `N*_warm` (compile excluded) and `N*_cold` (compile included) against each CPU baseline separately — `n_jobs=1` and `n_jobs=8` will not give the same answer, and the doc's number is currently unqualified.

| flux space, everywhere except one control cell | AIC/BIC/WAIC are not comparable across spaces (scripts/compare_at2017gfo.py:24-26). One kn1/mcmc/cpu-jax/flux cell tests the assertion that TIMING is space-independent. |
| abc_smc_gpu | runnable, but it does not set result.samples_by_chain (DEPLOYMENT_AUDIT.md section 5 item 11), so ess_summary has nothing to consume and its ESS/s would be iid_assumed guesswork on a sampler that is not iid. Include it once that is fixed. |

## What this benchmark does not license

1. **Cross-sampler speed comparison when the accuracy gate failed or was not run.** A struck-through
   ESS/s is not a slower number, it is *not a number*.
2. **Extrapolation to other datasets or models.** ESS/s depends on `n_data`, the parameter count,
   the forward-model cost and the posterior geometry. The `bazin` control cell exists precisely to
   expose how much of each sampler's cost is fixed overhead rather than model cost.
3. **"The GPU is N x faster" as a hardware claim.** The CPU and GPU arms run *different code paths
   for the same physics* — `predict` one curve at a time against `vmap(predict_jax)` at
   `chunk=16`. Every such ratio is whisper's CPU arm against whisper's GPU arm, never CPU silicon
   against GPU silicon.
4. **Anything about model quality.** AIC/BIC/WAIC compare **models**; they are carried so a reader
   can see whether a fast run was also a good one, never to rank samplers.
5. **Cross-space comparison.** A flux-space fit and a magnitude-space fit have different
   likelihoods over different data representations (`scripts/compare_at2017gfo.py:24-26`). The
   matrix fixes magnitude space and carries exactly one flux cell, and that cell is a control on
   *timing*, not an invitation to compare information criteria across spaces.
6. **Reproduction on a quiet machine.** Every number here was measured on a shared, loaded box.
   Rows that could not be trusted say so; rows that could still carry that box's noise floor.

## Known measurement gaps

- **NUTS forward-model / gradient evaluations** — whisper_cbpf/samplers/jax/nuts_gpu.py:170,179 pass extra_fields=('diverging',) only, so num_steps is never collected and leapfrog counts are unrecoverable from result.numpyro_mcmc. Reported as `unknown`. WHAT WOULD SETTLE IT: add 'num_steps' to both extra_fields tuples and report sum(num_steps) as GRADIENT evaluations (~2-4x the cost of a forward evaluation). Filed, not patched.
- **abc_smc_gpu ESS** — no result.samples_by_chain (DEPLOYMENT_AUDIT.md section 5 item 11); cell excluded rather than reported with a fabricated chain axis.
- **forward-model evaluation counts are exact only for `abc` and `abc_gpu`** — measured, not assumed: `--validate-evals` wraps a numpy model's `predict` in a counter and compares. `abc` matched exactly at every budget tried. `mcmc`/`emcee_jax` are an UPPER bound (a proposal outside the prior support returns -inf without calling `predict`, samplers/mcmc.py:46-48); `abc_smc` is an UPPER bound (`total_simulations` counts attempts, and post-round-0 attempts outside the support skip `predict`, samplers/abc_smc.py:77-78); `snpe` is a LOWER bound by a fixed, budget-independent +3. The shim cannot reach `n_jobs>1` (the counter lives in the forked child) or the JAX samplers (they call `predict_jax`).
- **nvidia-smi as a memory instrument** — useless under scripts/whisper-gpu-env.sh: XLA preallocates XLA_PYTHON_CLIENT_MEM_FRACTION of the card, so memory.used reports the pool, not the run. Peak memory comes from jax memory_stats()/torch; nvidia-smi is a CONTENTION signal only. jaxlib 0.10.2 also returns peak_bytes_reserved = 0, so our own footprint on the card is taken from bytes_limit (the pool) instead.
- **the GPU contention detector cannot see a neighbour smaller than ~2 GiB** — measured: our own non-pool footprint (CUDA context plus cuBLAS/cuDNN workspaces) ranged over 279-866 MiB across four cells on one card and one model, so a 512 MiB slack flags our own context as a neighbour. A real neighbour on the same card appeared as +19,991 MiB. The slack is therefore 2048 MiB, and anything smaller than that is invisible to this test. WHAT WOULD SETTLE IT: per-process attribution via nvidia-smi --query-compute-apps, which needs a PID namespace the container does not have.
- **foreign-PID attribution inside a container** — nvidia-smi --query-compute-apps reports PIDs from a namespace the container cannot map, so 'is this PID ours?' is unanswerable here. Each cell records contention.foreign_pid_detection to say whether the test was usable; the memory-excess and utilisation tests do not depend on PIDs.
